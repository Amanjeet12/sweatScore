### R01 — Durable onboarding and first-plan preparation

**Current files:** `app/index.tsx`; `app/(auth)/verify.tsx`, `setup-profile.tsx`, `setup-activity-goal.tsx`, `ask-push-permission.tsx`, `ask-health-permission.tsx`; `convex/users.ts`; `store/useAuthStore.ts`.

Current normal sequence is email/OTP → basic profile → activity goal → notification permission → health permission → subscription if needed → dashboard. There is no seven-question coach profile or five-question daily questionnaire in this onboarding sequence. Health success and skip both set `users.onboarded = true` before purchase. On a later login, `verify.tsx` sends an onboarded user directly to the dashboard. `app/index.tsx` checks missing profile/goal/permissions and onboarding status but does not restore a purchase/prepared-plan workflow.

`users.updateOnboarded` accepts a boolean and schedules the no-activity reminder on the initial false-to-true transition; it schedules MailerLite welcome-group work on every true call. Completion needs an idempotent transition so duplicate payment callbacks cannot repeat ancillary effects.

**Required change:** persist distinct onboarding stage, seven-question profile/version, health continuation state, daily answers/day, generation request/status and entitlement state. Final daily submission must atomically retain answers and reserve one logical request before navigating immediately to the paywall. Use a shared server-backed resume decision in initial routing, OTP completion, checkout, restoration and redemption. Do not infer progress from `onboarded`, route parameters or local component state alone. Replace the unguarded boolean completion transition with server validation of the required saved state and verified entitlement; old clients must not bypass this by setting `onboarded` directly.

Use the guide’s recommended purchase-button readiness gate so normal checkout reaches a saved ready plan. A verified purchase that races a pending/failed plan must still land on Today with honest preparation/retry status. Keep the valid entitlement. Cancellation, failure, app restart and re-login must resume the saved purchase stage without another questionnaire or automatic provider request. On a changed app day, preserve the old plan as history and explicitly obtain new daily answers.

**Reuse:** basic profile screen, OTP/auth, health permission/skip paths, UI chrome, local storage as a cache only. Keep optional notification permission after Today. Existing entitled members without a coach profile use profile → daily questions without another paywall.

### R04 — Coaching prompts, context, validation and generation state

**Current files:** `convex/progressCoachActions.ts:29`, `progressCoachPolicy.ts`, `progressCoach.ts:281–735`; `shared/progressCoach.ts`; `app/progress-coach/plan.tsx`; `components/core/CoachPresentation.tsx`; `shared/progressCoachChallenges.ts`.

This is not either supplied client prompt. The current policy uses 1/10/20/30-minute options, generic strength/cardio/core/gentle movement, a 10% step-increase cap, an upper step bound, carbohydrate servings and a separate hydration field. Sore upper body maps to cardio and sore lower body to core, unlike the new opposite-body strength rules.

`loadTrackingSummary` summarizes seven previous `trackDaily` dates into usable-day count, average steps/active minutes and active days. Provider input has no dated weight history, dated workout history, streak or recent plans; weight is excluded from `profileForGeneration`. `trackDaily` can contain zero-step days created by non-step activity, so counting every row as usable step evidence needs correction. `loadCoachContext` reads the latest mutable profile during execution rather than a profile snapshot/version attached to the request.

Useful existing protections: one current plan lookup per user/date, scheduled server generation, attempt counters, stale-result guards, provider timeout/error codes, usage/latency metadata, and saved output. `startTodayPlan` reuses every existing status, including failed and fallback, so there is no effective deliberate retry/refresh path. The watchdog automatically retries stale attempts up to two, then stores generic fallback output. Provider failures also become fallback plans. Pain bypasses the provider and saves legacy rest/nutrition fallback. All of this must be reconciled with truthful failure states and the supplied prompt.

**Required change:** retain both client base prompts and every example intact and versioned; adopt six validated strings: `headline`, `workout`, `steps`, `sleep`, `meals`, `why`. Preserve exact required headlines/rest/sleep text, named workout types and durations, strength frequency, soreness split, recovery reasoning and steps rounded to 500 with no more than 2,000 above a valid average. Missing history uses 5,000/7,000 per the prompt and never an invented average. Include all five answers, all available profile answers, dated steps/workouts, reliable average, streak and seven-day recent plans, clearly separated from completed activity.

Store an immutable input snapshot, profile/prompt/tone versions, request ID, generation attempt and plan revision. Freeze configuration at request reservation. A late response cannot replace a newer revision. Failed generation must remain failed with saved answers and an explicit retry action; do not substitute old generic coaching. No calls from payment, app launch, mount, plan reopen or ordinary activity logging.

The provider’s current 500-output-token cap and four-field length limits were designed for the old short response. Review sizing against all full client examples and six fields; do not truncate valid content into a misleading ready plan. Keep timeout/usage/error instrumentation and redact sensitive media/context from logs.

**Follow-up finding:** no immediate “how did it go?” post-plan completion question/trigger was found in the inspected coach routes, presentation components or backend. `plan.tsx` instead offers an optional generic challenge mapping. Record the reported issue as a regression criterion, not a confirmed code defect in this checkout. The mapping from generic strength to “Full Body” is not a valid assignment source for a saved lower-body plan and must not be reused for that purpose.

## 5. Proposed persistence and compatibility design

Use additive schemas or a version discriminator so deployed old records remain readable. Exact table names can be chosen in implementation; the required responsibilities are:

| Record responsibility | Required persisted context |
| --- | --- |
| Onboarding progress | Authenticated member, stage, profile/version, health continuation, daily-answer reference/day, first-plan request/revision, entitlement reconciliation state, completion transition ID/time. |
| Profile and weight history | Canonical answers/schema version, immutable version or snapshot, weight value/unit/date and normalized value where useful; preserve provenance of migrated observations. |
| Daily answers | Member, app day/timezone snapshot, all five canonical answers, completion status/time. Partial draft is not a completed questionnaire. |
| Plan request and revision | Input snapshot, profile/prompt/tone versions, request idempotency key, pending/ready/failed status, attempts, validated six-field output, structured validated assignment metadata, usage/error fields. |
| Daily assignment | Member/day/category, plan ID/revision, exact recommendation and relevant targets; unstarted, started, completed or superseded state. |
| Proof/submission | Owner, original assignment revision, capture session/media IDs, upload status, submission token, completion record. Partial submission cannot silently switch revision. |
| Category reward slot | Stable member/day/category/slot identity independent of plan revision; one slot for Workout/Sleep/Steps, three for Meals; canonical links to legacy/new activity and reward. |
| Meal analysis | Owner/day/draft/media, verified goal/workout context, prompt/tone versions, scan-attempt reservation/count, pending/ready/failed result, nullable verdict, feedback, shared transaction ID. |
| Entitlement | Provider identity, verified status/source/time and event/reconciliation key; never merely a client assertion. |
| Tone configuration | Enumerated settings, scope, version, editor/time, restore history, expected-version conflict handling; separate preview usage. |

Plan identity and revision are different: one logical daily plan may have a refreshed revision. Category reward identity must remain stable across those revisions. A server transaction must reserve requests/slots and reject or reuse duplicates across devices. A retry should return the already committed completion where possible rather than write a second post or award.

### Migration constraints

1. **Preserve history.** Do not overwrite old plan outputs, answers, schedule windows, completion values or point totals to make them look like new-schema records. Historical unknown plan context remains explicitly legacy/unknown.
2. **Profile migration.** Preserve old values and optional extra questions. Map only semantically equivalent fields; require genuine answers for non-equivalent new choices. A last known weight can be imported with its known observation/update timestamp and provenance; do not invent earlier measurements.
3. **Current-day category limits.** Reconcile both legacy `challengeCompletions` of type `check_in` and activity logs such as `gym_workout`/`workout` before accepting new Workout claims. Meal/Sleep/Steps logs consume corresponding slots. Legacy hydration is currently aliased to Gym in the app; this is not proof of a workout. Inspect real records and approve an explicit mapping rather than blindly treating hydration as trained-today evidence.
4. **Already earned rewards.** Do not recalculate historical Sleep 3 or Steps 5 points into new rates, claw back earned points, or award a new Workout reward because the old tile name changed. Preserve multiple historical rewards if they already exist while closing new eligibility for that category/day.
5. **In-flight work.** Preserve original capture/submission day and context when available; an old queue without enough metadata cannot be assigned an invented plan version. Reconcile legacy uploads through a documented compatibility path and block duplicate reward claims. Finalization after midnight needs the policy decision in section 9.
6. **Old clients.** New writer guards and canonical eligibility must cover old completion/post mutations as well as the new UI. Use existing app-version/force-update infrastructure only if a minimum version is needed; do not silently orphan paid users or their queued media.
7. **Read-model consistency.** Update Today ticks, count queries, banner statistics, streak helper, tracking rollups, leaderboard and feed enrichment together. New records must not be counted once as an activity and again as a separate reward. Recompute only affected data with before/after totals and resumable migration checkpoints.
8. **Retirement snapshot.** Record legacy schedule state before deactivation. Preserve fields/history or archive them explicitly; add disabled/retired state rather than invoke destructive removal paths. Inventory/cancel only identified legacy jobs. Keep a migration ledger and verify reruns make no new changes.
9. **Access and retention.** Extend account deletion and media-retention handling in `convex/users.ts`/related admin deletion paths to new records. Protect private photos and meal feedback. Do not make immutable audit context an excuse to bypass existing account deletion policy.
10. **Rollback.** Roll back readers behind a release switch only to compatible readers of existing data. Never re-enable shared scheduling or reset category slots as an automatic rollback of a new UI. Retain new record versions and historical records.

### Day boundaries and data trust

Backend plans and activity eligibility primarily use the member’s stored timezone, default UTC, through `convex/utils/timezone.ts`. Legacy admin schedules use `Europe/London`; the featured card then maps the alternating schedule into the member’s local day. Today caches use device date/timezone in places. Coach queries use `Date.now()` without a refresh argument/timer, so a mounted query cannot be assumed to update at midnight without an invalidation trigger.

Use the existing member-local server day consistently for new plan, assignment, quota and streak state, with server-provided day/next reset and explicit foreground/midnight refresh. Test DST, timezone changes and late checkout. Do not globally convert community-challenge schedules from London as part of this work.

`activities.syncHealthData` authenticates a user but passes caller-supplied `args.userId` into writes without checking equality with the authenticated ID. Fix that ownership boundary before treating health context as reliably attributable to the member. Distinguish observed zero steps from missing step coverage; aggregate rollups alone do not establish sensor coverage. Workout history must come from actual completed workout records, not every habit, every challenge or recent generated plans.

## 8. Cross-stage acceptance invariants

- Completing questions, preparing a plan, creating assignments, purchasing and opening Today/plan are not activity completions. They never grant category points or advance the streak.
- A first plan is reserved from saved answers before checkout, and a successful verified same-day purchase resumes that exact saved result. Payment is never a generation trigger.
- Generation state, entitlement state, questionnaire state and activity state are independent and persisted.
- Current plan guidance is member-specific; completed and in-flight proof keeps its originating plan revision. No generic shared strength assignment may replace it.
- Category slots are member/day/category based, not plan-version based. Old and new writers share one eligibility decision.
- No current plan means no fabricated assignment. Rest/pain means no mandatory workout.
- A missing/failed AI response remains visible as unavailable/retryable; no canned success output or fabricated meal verdict.
- Scheduler retirement preserves code/history and disables producers, consumers, recurrence and queued callbacks selectively.
- The same server day drives plan, timer, category limits and meal counters. Historical plans are never relabelled as today.
- Tone administration changes style only, applies to future permitted requests and never exposes arbitrary prompt editing.
